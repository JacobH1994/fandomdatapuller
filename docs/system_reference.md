# System Reference

As-built description of what currently exists in this repository — what
the code does, not what it's meant to do. `docs/esports_fandom_platform_prd_v2.md`
covers intent, design rationale, and phase planning; this document covers
present-tense reality, generated by reading the code, schema, config, and
notebooks directly. Where the two disagree, this document describes what
the code actually does and flags the divergence.

Row counts, coverage figures, and "currently N rows" statements below are
a snapshot as of 2026-09-10 and will drift — regenerate this file rather
than hand-editing it (see CLAUDE.md).

**Neither `channels.yaml` nor `channels_youtube.yaml` accepts a channel URL** — both files' own header comments spell out the exact match key: a Twitch login (e.g. `esl_csgo`, not `https://twitch.tv/ESL_CSGO` and not the display name `ESL_CSGO`) for the former, a YouTube channel ID (e.g. `UCz3IJEo6bU3-Sl6PU5S9tqQ`) for the latter. Populating either is a plain YAML edit under the existing `channels:` key, keyed by `title_id` from `titles.yaml` — no code change, no script to run afterward (the next collector run just picks it up). Deliberate design decisions made curating the first two titles, worth following for the remaining 21: personality/co-stream channels that draw tournament-window viewing (e.g. popular CS co-streamers) are excluded even when a draft candidate surfaces them — `broadcast_tier`'s `detected_costream` already tracks that case separately, and folding them in here would blur, not sharpen, the distinction; a multi-game organization's general channel (e.g. BLAST's or PGL's own non-CS-specific account) is excluded too, since this file has no per-stream title-conditional mechanism to ringfence it to just one title's content.

## 2. Data flow and dependency order

```
Twitch Helix API      YouTube Data API      Steam Web API          Liquipedia MediaWiki API
      |                      |                     |                        |
      v                      v                     v                        v
twitch_poll.py        youtube_poll.py        steam_poll.py            liquipedia.py
      |                      |                     |                        |
      v                      v                     v                        v
data/raw/twitch/*     data/raw/youtube/*     data/raw/steam/*         tournaments (direct write,
                                                                       no raw-file backup)
      |                      |                     |                        |
      +----------------------+---------------------+                        |
                             |                                               |
                             v                                               v
                    etl/load_snapshots.py  <----------------------------------+ (also loads data/reference/*.jsonl)
                             |
                             +--> viewership_snapshots, language_mix_snapshots, platform_totals,
                             |    channels, steam_player_counts, steam_release_cohort,
                             |    steam_cohort_player_counts
                             v
              etl/generate_tournament_aliases.py  (reads tournaments, needs it populated first)
                             |
                             +--> tournaments.series_key, tournament_aliases
                             v
              etl/export_reference_data.py  (reads tournaments + tournament_aliases + steam_release_history)
                             |
                             +--> data/reference/*.jsonl  (committed — closes the load_snapshots.py rebuild loop)
                             v
              etl/classify_broadcast_tier.py  (needs viewership_snapshots AND tournaments/tournament_aliases)
                             +--> viewership_snapshots.broadcast_tier

collectors/kaggle_import.py  (independent one-time path)
      +--> monthly_category_history  (covered by data/reference/monthly_category_history.jsonl since 2026-09-09 — see §5)

collectors/steam_catalog_backfill.py  (Track A, independent one-time/on-demand path)
      +--> steam_release_history  (covered by data/reference/steam_release_history.jsonl since 2026-09-08)

collectors/steam_discovery_poll.py --> data/raw/steam_discovery/*  --> (via load_snapshots.py) steam_release_cohort
collectors/steam_cohort_poll.py    --> data/raw/steam_cohort/*     --> (via load_snapshots.py) steam_cohort_player_counts
```

**Hard ordering constraints**:
1. `load_snapshots.py` before `generate_tournament_aliases.py` before `export_reference_data.py` before `classify_broadcast_tier.py` — each reads what the previous step wrote. This is the exact order `scripts/local_refresh.sh` runs them in.
2. `collectors/liquipedia.py` must run (or `data/reference/*.jsonl` must already be loaded) before `generate_tournament_aliases.py` — it operates on `tournaments`, which only `liquipedia.py` or a reference-data reload populates.
3. `classify_broadcast_tier.py` degrades gracefully, not silently wrong, when run before aliases exist: a tournament with no `series_key` simply produces no co-stream candidates for that tournament — rows fall through to `general`.
4. `kaggle_import.py` has no ordering dependency on anything else.
5. `steam_cohort_poll.py`'s workflow runs `load_snapshots.py` first, unlike every other collector's workflow, since it needs to query `steam_release_cohort` (populated by `steam_discovery_poll.py`'s own committed raw files) for which `app_id`s are due.
6. `official_channel_candidates.ipynb` (step 3 of `local_refresh.sh`) only needs `viewership_snapshots` and `tournaments`.

**GitHub's own `schedule` trigger was confirmed unreliable for this repo, 2026-09-10** — a week of `poll.yml` run history showed a real average gap of 3.8h against the configured 1h cron, present well before this repo had many concurrently-scheduled workflows (ruling out our own concurrency as the cause). `dispatch_hourly.yml`/`dispatch_daily.yml` exist to work around this — `workflow_dispatch` (API-triggered) runs weren't subject to the same delay in this same check. Every underlying collector **keeps its native `schedule:` trigger too**, as a free fallback, not a replacement — this is additive. See `docs/external_scheduler_setup.md` for the external (account-gated, not something committed to this repo) half of this setup: a fine-grained PAT and two scheduled HTTP calls on a free cron service.

**External cron dispatcher status: PAT generated and a cron-job.org hourly job pointed at `dispatch_hourly.yml` were set up 2026-09-10, but as of this snapshot are NOT yet confirmed actually firing on schedule.** `gh run list --workflow=dispatch_hourly.yml` shows exactly one `workflow_dispatch` run total (2026-09-10T10:16:57Z, triggered by the repo owner's own GitHub account — consistent with either a manual `gh workflow run` test or a one-off "test this job" button in cron-job.org's UI, not evidence of a recurring fire). Checked again roughly one hour after the user said the cron job had just been created (~17:00 UTC) — still zero new `workflow_dispatch` runs as of 18:00 UTC. This does not necessarily mean the job is broken (it may simply not have hit its first scheduled tick yet, depending on exactly when in the hour it's set to run), but it means the fix is **not yet verified end-to-end** — do not treat `poll.yml`'s cadence as solved until a `workflow_dispatch`-triggered run is observed recurring hourly over a real stretch of time, per `docs/external_scheduler_setup.md`'s own verification steps.

All collector workflows now push with fetch+rebase+retry (not a bare `git push`) — added 2026-09-08/09 after two real, independently-diagnosed incidents (a Steam-poll lost commit, a Steam-discovery-poll lost ~25 minutes/1,021 classified apps) where a bare push got rejected by a concurrent collector's push to `main` and, under `set -e`, silently killed the job with the local commit never reaching the remote. Safe here because every collector writes to its own distinct `data/raw/<platform>/` subtree — a concurrent commit from another workflow never conflicts at the content level, only at the ref-update level. The two dispatcher workflows don't write anything themselves (no `permissions: contents: write`), so they're outside this concern entirely.

The similarity/crossover tracker's own scheduled Action, referenced in PRD §9.6b and previously (incorrectly) described in this document and the PRD as resolved, **does not exist** — reopened as a build task 2026-09-09 (see PRD §19).
